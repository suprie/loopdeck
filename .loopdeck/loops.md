This isn't cosmetic: `claude_session.rs::answer_control_request` only parks an `AskUserQuestion`/manual-approval/plan-approval card when a channel is present — the non-streaming path auto-denies it immediately, so Phase 2/3 could never actually observe a mid-run stall. **New `AppError::TurnParked(String)` variant** (distinct from the catch-all `Agent`) lets an unattended caller tell "nobody was there to answer" apart from a real turn failure without parsing message text. `turn_deadline_expired_error` (fires once the existing `TURN_DEADLINE`, 30 min, elapses on a parked card) now takes a `pending_detail` describing what was pending — updated at all three park sites: `answer_ask_user_question` (the question text), `answer_manual_permission` (`tool_name` + input), `answer_plan_approval` (the plan) — capped at 200 chars so a large `Write`/`Edit` input or long plan can't blow up the message. `commands/run_queue.rs::execute_run` matches `Err(AppError::TurnParked(detail))` ahead of the generic `Err(e)` arm: the phase becomes `Parked` (not `Failed`) with `park_payload = detail`. New pure `run_executor::phases_blocked_by_park(plan, parked_id, policy)` (unit-tested: transitive dependent chain, unrelated phase stays queued, non-`Queued` phases ignored, `halt` blocks everything remaining) computes which other `Queued` phases the plan's `StallPolicy` also blocks — under `continue_independent` only the parked phase's `depends_on` dependents (transitively), marked `Parked` with a `"blocked: depends on parked phase …"` payload; under `halt`, every remaining `Queued` phase. Both cases reuse the *same* code path with **no early-return branch**: a policy that blocks nothing leaves the loop free to advance to the next `Queued` phase naturally, and a policy that blocks everything leaves nothing for the loop's own top-of-iteration status check to pick up — so the run ends there without a separate `halt` special case. `execution.yaml`'s `current` loop is `abandon_current`'d (same as the `Failed` path, reason = the park detail) rather than left dangling, since `continue_independent` needs `current` cleared to promote the next phase, and by the time it does, that phase's `spawn_fresh` would replace the parked session anyway (Phase 2's existing "fresh process per phase" design) — there's no still-resumable session worth preserving by leaving `current` untouched. **Known, documented ceiling** (not fixed — out of this PRD's scope): a stall is only detectable once `TURN_DEADLINE` elapses, because `claude_session.rs`'s park site isn't selected against any cancellation once entered (its own doc comment: "during a parked approval/question the loop is off the read, so an interrupt there won't be observed this turn") — bounding it tighter needs a larger session-model change (environment, not this PRD's sequencing/state scope). In the common case this costs nothing: a human watching the app live sees the same pending card via the existing `agent_pending_question`/`_permission`/`_plan` surfaces (shared `AppState`, not tied to the run's no-op channel) and can answer it directly, so the turn completes normally and `TurnParked` is never reached. `cancel_run`'s doc comment corrected to match: `fire_interrupt` now genuinely interrupts an *actively streaming* phase turn, but still can't reach an already-parked card. 7 new/updated Rust tests (`turn_deadline_expired_error` × 2, `phases_blocked_by_park` × 4 in `run_executor.rs`, plus the 3 call-site updates).
