## 2026-07-28 — `prd-run-queue` Phase 1: RunPlan is data-only, no OCC/backup; budgets are recorded not enforced

- **Status**: accepted
- **Context**: `prd-run-queue.md` Phase 1 asks for `RunPlan`/`RunPhase`/`StallPolicy`/`RunBudgets` structs with serde defaults and atomic persistence to `.loopdeck/run-plan.yaml`, referencing phases by stable execution ID. The closest precedent, `execution.rs` (0.2.1), additionally carries an optimistic-concurrency `revision` field and `.bak`-backed non-destructive recovery — but that machinery exists specifically because `execution.yaml` has multiple concurrent writers (the `loopdeck state` CLI, IPC commands, and the migration path). A run plan has exactly one writer: the in-app executor that will exist from Phase 2 onward. Also, the PRD's own Non-Goals explicitly separate this PRD's job (sequencing and state) from `prd-unattended-ship`'s job (budget *enforcement*) — Phase 1 only needed a place to record the queue-time budget values, not a spend tracker.
- **Consequences**: `src-tauri/src/runplan.rs` intentionally omits `execution.rs`'s revision/OCC and `.bak` recovery — `load`/`save` are a plain bounded-read-and-parse / atomic-write pair, no `expected_revision` parameter, no backup file. If Phase 2's executor turns out to need concurrent writers after all (e.g. a UI cancel racing an executor status update), add the OCC field then — no data already on disk breaks, since `revision` would arrive as a new `#[serde(default)]` field like `execution.rs`'s did. `RunBudgets` fields (`per_phase_token_cap`, `per_phase_wall_clock_secs`, `total_run_wall_clock_secs`) are all `Option<u64>`, documented as "`None` means use `prd-unattended-ship`'s named-constant default, not unbounded" — this module never reads or enforces them, only stores what the picker UI (Phase 5) will write. Mirrors `execution.rs`'s Phase 2→3 pattern: a module-level `#![allow(dead_code)]` covers the currently-uncalled `pub` surface until Phase 2's executor + IPC commands become the first production callers; remove the allow then, not before.

## 2026-07-28 — `prd-run-queue` Phase 3: interview answers extracted via a greppable text marker, not raw tool-call plumbing

- **Status**: accepted
- **Context**: The PRD's Design section says the pre-flight interview reuses "the existing question-card IPC surface" — a bounded session whose `AskUserQuestion` calls render as the same cards chat already shows. `start_fresh_and_record` already parks and resumes on those cards internally (via `ParkSlots`/`QuestionSlot`), but it returns only the turn's final `AgentResponse`, not the raw `QuestionAnswers` map exchanged mid-turn — plumbing that map out would mean touching `claude_session.rs`'s park/resume internals for a one-off consumer.

## 2026-07-28 — "Start next loop" skips `Review & merge:` reminders instead of "implementing" them

- **Status**: accepted
- **Context**: `loopdeck-open-pr`'s Phase 7 appends `- [ ] Review & merge: <url>` to `.loopdeck/loops.md`'s `## Next Steps` as a human bookkeeping reminder. `next_unchecked_loop_step` (`commands/agent.rs`) treated every `- [ ]` line in that section as equally actionable, so after a user merged a PR and pulled, "Start next loop" picked the still-unchecked merge reminder and told the agent to "implement" it — the agent's only compliant move was to check the box, which read to the user as the app silently marking a real task done instead of starting new work.
- **Consequences**: `next_unchecked_loop_step` now skips any `- [ ] Review & merge:` line (case-insensitive prefix match) and keeps scanning for the next real step; if only reminders remain it falls through to the existing "propose the next loop" prompt instead of fabricating work. Fix is scoped to the one function with the false positive — did not touch `loopdeck-open-pr`'s insertion behavior, since the reminder itself is still useful for a human. Flagged as a background task: the distinction is still a hardcoded string match rather than part of the `loops.md` format itself, so a future skill adding a different non-actionable reminder type would reproduce the same bug class.

## 2026-08-03 — Transcript reads keep the tail, not the head, once a file exceeds `TRANSCRIPT_MAX_BYTES`

- **Status**: accepted
- **Context**: The 2026-08-01 attachment work flagged "watch transcript growth" as a follow-up — inline base64 images (up to `ATTACHMENTS_MAX_TOTAL_BYTES`, 8 MiB, per turn) make the existing 16 MiB `TRANSCRIPT_MAX_BYTES` cap reachable within a handful of image-heavy turns, instead of the "hundreds of turns" the cap was sized for. Investigating the actual behavior at that cap surfaced a latent correctness bug, not just a sizing question: `limits::read_bounded_to_string` reads the first `max_bytes` of a file (`File::take`), but every caller in `conversation.rs` uses it on `active.jsonl` — an append-only, still-growing log where the newest turns are at the *end*. Once a transcript exceeded the cap, `load_conversation_by_id` would silently show only the *oldest* turns and hide everything recent from the UI; `append_terminal_if_orphan` (whose own doc comment says "only the tail matters") would read a stale head-truncated window and could miss a genuine crash orphan at the real end of the file; and `session_id_for_conversation` (used by `promote_to_active` to resume a session) could resolve a stale mid-file session id instead of the real most-recent one. All three were previously an extreme, rarely-hit edge case; inline images make them realistic.
- **Consequences**: Added `limits::read_bounded_tail_to_string` — same lossy-decode contract as `read_bounded_to_string`, but seeks to `len - max_bytes` on an oversized file (logging a `warn!` with the path/len/cap, so the growth is now visible instead of silent) and drops the one partial leading line the seek may have landed inside, instead of the original's arbitrary trailing partial line. Switched the three tail-sensitive call sites in `conversation.rs` (`load_conversation_by_id`, `promote_to_active`, `append_terminal_if_orphan`) to the new reader. Left `list_conversations`'s per-file summary read on the original head-reader: `summarize` wants the *first* user turn for its excerpt, and a wrong `last_ts`/`turn_count` on an oversized file is a cosmetic history-list imprecision, not silent data loss or a broken resume — consistent with this module's documented "budgets are DoS guards, not correctness limits" stance for that one call site. `TRANSCRIPT_MAX_BYTES` itself is unchanged (16 MiB) — raising it doesn't fix the direction bug and a real image-heavy-conversation ceiling wasn't measured; the actionable fix was correctness (keep the relevant end), with the new `warn!` log giving real visibility into how often the cap is actually hit in practice, which is better evidence for a future resizing decision than a guess would be.
- **Detail**: 3 new tests in `limits.rs` (`read_bounded_tail_returns_full_small_file`, `read_bounded_tail_keeps_newest_lines`, `read_bounded_tail_missing_file_errors`). Gates green: `cargo fmt --check` / `cargo clippy --lib -- -D warnings` / `cargo test --lib` (524 passed, +3, 8 ignored). No frontend change, so `tsc`/`build` not run.
