## 2026-08-04 — Run-queue reliability: verdict marker must survive to the final message; branch names are now descriptive

- **Status**: accepted
- **Context**: A live overnight run (`run-a3a5f38c-…`) parked all 6 batched phases with "no verify verdict found in the turn's final response" even though the agent's own activity log said "All 6 loops done, verified, shipped." `extract_verdict` (`run_executor.rs`) greps only `response.result` — the turn's *final* chat message — not the full transcript; the agent had stated `**Verdict:** PASS` earlier (inside the `loopdeck-prd-verifier` report) but its final wrap-up message was free-form prose that never repeated the marker line, so extraction found nothing. Considered and rejected: auto-marking a phase complete when no verdict is found — that would silently ship any turn that got cut off or forgot the marker, defeating the "nothing ships un-verified" gate this whole epic is built on (ADR-5). Separately, the run's git branch landed as the opaque `run/run-a39aa17d-…` — no indication of what work it covered.
- **Consequences**: `build_combined_phase_prompt` (`run_executor.rs:174-186`) now explicitly instructs the agent that its own final chat message (not just the PR body) must end with the literal `**Verdict:** PASS`/`WARN`/`BLOCK` line, restated even if already stated earlier in the turn. `run_branch_name` (`run_queue.rs`) now derives the branch from the first queued phase's `execution_id` (already `<prd-slug>/<loop-slug>`) plus a short id suffix for uniqueness, e.g. `run/wake-up-notify-after-completed-922a0bfc6c7e`, with a `-plusN` suffix noting multi-phase batches — sanitized once at the end so no unsafe characters leak into the branch name regardless of slug/suffix shape. `extract_verdict`'s strict "missing marker → does not advance" behavior is unchanged; this only fixes the prompt so the marker reliably reaches the text it's graphed. 4 new Rust tests (1 prompt-content assertion, 3 branch-name cases: single-phase slug, multi-phase `-plusN`, unsafe-character sanitization). Gates green: fmt/clippy(lib, `-D warnings`)/test(589 passed, +4, 8 ignored). No frontend change. The 6 already-parked phases from the affected run need a manual "Retry unattended" — their prompt was built before this fix.

## 2026-08-03 — Transcript reads keep the tail, not the head, once a file exceeds `TRANSCRIPT_MAX_BYTES`

- **Status**: accepted
- **Context**: The 2026-08-01 attachment work flagged "watch transcript growth" as a follow-up — inline base64 images (up to `ATTACHMENTS_MAX_TOTAL_BYTES`, 8 MiB, per turn) make the existing 16 MiB `TRANSCRIPT_MAX_BYTES` cap reachable within a handful of image-heavy turns, instead of the "hundreds of turns" the cap was sized for. Investigating the actual behavior at that cap surfaced a latent correctness bug, not just a sizing question: `limits::read_bounded_to_string` reads the first `max_bytes` of a file (`File::take`), but every caller in `conversation.rs` uses it on `active.jsonl` — an append-only, still-growing log where the newest turns are at the *end*. Once a transcript exceeded the cap, `load_conversation_by_id` would silently show only the *oldest* turns and hide everything recent from the UI; `append_terminal_if_orphan` (whose own doc comment says "only the tail matters") would read a stale head-truncated window and could miss a genuine crash orphan at the real end of the file; and `session_id_for_conversation` (used by `promote_to_active` to resume a session) could resolve a stale mid-file session id instead of the real most-recent one. All three were previously an extreme, rarely-hit edge case; inline images make them realistic.
- **Consequences**: Added `limits::read_bounded_tail_to_string` — same lossy-decode contract as `read_bounded_to_string`, but seeks to `len - max_bytes` on an oversized file (logging a `warn!` with the path/len/cap, so the growth is now visible instead of silent) and drops the one partial leading line the seek may have landed inside, instead of the original's arbitrary trailing partial line. Switched the three tail-sensitive call sites in `conversation.rs` (`load_conversation_by_id`, `promote_to_active`, `append_terminal_if_orphan`) to the new reader. Left `list_conversations`'s per-file summary read on the original head-reader: `summarize` wants the *first* user turn for its excerpt, and a wrong `last_ts`/`turn_count` on an oversized file is a cosmetic history-list imprecision, not silent data loss or a broken resume — consistent with this module's documented "budgets are DoS guards, not correctness limits" stance for that one call site. `TRANSCRIPT_MAX_BYTES` itself is unchanged (16 MiB) — raising it doesn't fix the direction bug and a real image-heavy-conversation ceiling wasn't measured; the actionable fix was correctness (keep the relevant end), with the new `warn!` log giving real visibility into how often the cap is actually hit in practice, which is better evidence for a future resizing decision than a guess would be.
- **Detail**: 3 new tests in `limits.rs` (`read_bounded_tail_returns_full_small_file`, `read_bounded_tail_keeps_newest_lines`, `read_bounded_tail_missing_file_errors`). Gates green: `cargo fmt --check` / `cargo clippy --lib -- -D warnings` / `cargo test --lib` (524 passed, +3, 8 ignored). No frontend change, so `tsc`/`build` not run.

## 2026-08-03 — Route the secret scan through a real `loopdeck secret-scan` CLI instead of markdown-embedded `rg`

- **Status**: accepted
- **Context**: `prd-unattended-ship.md`'s two remaining gaps after PR #48 were both in the unattended draft-PR tail. The staged-diff secret scan (P1 goal) lived only as an inline `rg` pipeline inside the `loopdeck-open-pr` skill's old Phase 6a — run *after* Phase 5b's `git push`, so a hit was already on the remote by the time it fired. The `loopdeck-open-pr` skill's Phase 5a now runs it immediately after `git add -A` and before the commit, for unattended pre-authorized runs only — the earliest point in the flow a hit can still be stopped before anything reaches the remote. 10 new Rust tests, including 3 CLI-level tests against real temp git repos (staged secret → exit 1, clean staged diff → exit 0, unknown flag → exit 2) that exercise the actual abort path end-to-end.
