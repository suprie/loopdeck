## 2026-07-28 — `prd-run-queue` Phase 4: stalls only detectable via streaming + `TURN_DEADLINE`, not interrupted early

- **Status**: accepted
- **Context**: Detecting a mid-run `AskUserQuestion`/permission/plan stall requires the executor's phase turns to run through the streaming pipeline (the non-streaming path auto-denies these cards instead of parking), and `claude_session.rs`'s park site can't be cancelled early — it isn't selected against any interrupt once entered, only against its own 30-minute `TURN_DEADLINE` backstop.
- **Consequences**: `execute_run` now sends each phase via `start_fresh_and_record_streaming` with a no-op sink channel and catches the new `AppError::TurnParked` (fired at `TURN_DEADLINE`) to mark the phase `Parked` instead of `Failed`; a pure `run_executor::phases_blocked_by_park` then applies the plan's `StallPolicy` to the remaining `Queued` phases. A stall is unavoidably a ~30-minute-worst-case cost per phase in this codebase's current single-session-per-project architecture — shortening it needs a session-model change out of this PRD's sequencing/state scope.
- **Detail**: `.loopdeck/loops.md` `## Current` (2026-07-28 `prd-run-queue` Phase 4 entry) has the full file/symbol breakdown.

## 2026-07-29 — Wired `RunConsent.draft_pr_authorized` through to a real unattended-draft-PR bypass

- **Status**: accepted
- **Context**: `RunConsent.draft_pr_authorized` (`runplan.rs`) has existed since Phase 1 with a doc comment claiming it "authorizes `gh pr create --draft` with no interactive confirmation" — but it was dead: never read by `run_executor`/`run_queue`, and `loopdeck-open-pr`'s Phase 4 confirm gate had zero conditional/bypass language, so a queued overnight run could never actually open a PR without a human present to answer "proceed, edit, or abort?".
- **Consequences**: `build_phase_prompt` (`run_executor.rs`) now takes `draft_pr_authorized: bool`, threaded from `plan.consent.draft_pr_authorized` at its one call site (`commands/run_queue.rs::execute_run`); when true it tells the agent, in plain text, that this run is pre-authorized to skip `loopdeck-open-pr`'s Phase 4 confirmation and open Phase 6 as `gh pr create --draft` (no `--web`) — the `false` branch reproduces the prior prompt text byte-for-byte, so non-consented runs are unaffected. `loopdeck-open-pr`'s SKILL.md (and its byte-identical mirror in `templates/skills/loopdeck-open-pr/`) gained a new Phase 4a that checks for that exact stated authorization before the (unchanged) Phase 4b confirmation gate, plus a `--draft`/no-`--web` Phase 6a variant — the confirm gate stays the unconditional default for every interactively-invoked run; only a run whose prompt explicitly states pre-authorization can skip it. Draft-only is enforced in both the prompt text and the skill doc: nothing in this change ever readies or merges a PR automatically.
- **Detail**: The interactive "Start next loop" path (`commands/agent.rs`) is untouched — it always confirms, by design, matching the session's own publish-safety rules. The Phase 5 picker UI that would let a human actually set `draft_pr_authorized=true` from the app doesn't exist yet (out of scope here); this only finishes the executor↔skill wiring for when that UI lands. See PR #33 (same session) for the complementary fix: `next_unchecked_loop_step` now skips `- [ ] Review & merge:` bookkeeping lines instead of "implementing" them — relevant because Phase 7 still appends that same reminder line after a draft PR opens, and a human still has to act on it manually.

## 2026-08-01 — `create_run_plan`: the missing write path a picker UI needs to exist at all

- **Status**: accepted
- **Context**: Implementing `prd-run-queue` Phase 5 (phase picker UI) surfaced a gap the PRD's Design section hadn't named: `queue_run`/`run_phase_interview`/`skip_phase_interview` all *read* `.loopdeck/run-plan.yaml` via `runplan::load`, but nothing in Phases 1-4 ever *wrote* a fresh plan from a set of selected phases — Phase 1's tests construct a `RunPlan` directly in Rust, and there was no IPC path for a picker selection to become one.
- **Consequences**: New pure `run_executor::build_run_plan(id, project, created, execution_ids, stall_policy, draft_pr_authorized) -> RunPlan` builds the phase list with `depends_on` defaulting to the authored/selection order (each phase depends only on its immediate predecessor), matching the PRD's "linear chain, no editor" v1 lean — kept pure and unit-tested (no `AppState`, no disk I/O) per this module's existing split between domain logic here and `AppState`-dependent glue in `commands/run_queue.rs`. The new `create_run_plan` command validates every ID against `epic::find_loop_by_id` before writing (a stale/renamed ID is rejected at queue time, not discovered mid-run), refuses while a run is already in progress (the same `run_handles` guard `queue_run` already uses), and otherwise replaces any existing plan outright — a fresh picker selection is always meant to start a new plan, not merge into a stale one from a previous night.
- **Detail**: `.loopdeck/loops.md` `## Current` (2026-08-01 `prd-run-queue` Phase 5 entry) has the full frontend breakdown, including why the Interview UI checklist item needed no new question-card plumbing (it reuses `ProjectDetail.tsx`'s existing tab-agnostic `StuckQuestionCallout`).

Corrected the false claim in both `prd-run-queue.md`'s Phase 5 checklist and `loops.md`'s Phase 5 changelog entry, cross-referencing this decision. Gates green: fmt/clippy(lib, `-D warnings`)/test(484 passed, 8 ignored). No frontend change (the bug was purely a backend pipeline choice).

## 2026-08-03 — Transcript reads keep the tail, not the head, once a file exceeds `TRANSCRIPT_MAX_BYTES`

- **Status**: accepted
- **Context**: The 2026-08-01 attachment work flagged "watch transcript growth" as a follow-up — inline base64 images (up to `ATTACHMENTS_MAX_TOTAL_BYTES`, 8 MiB, per turn) make the existing 16 MiB `TRANSCRIPT_MAX_BYTES` cap reachable within a handful of image-heavy turns, instead of the "hundreds of turns" the cap was sized for. Investigating the actual behavior at that cap surfaced a latent correctness bug, not just a sizing question: `limits::read_bounded_to_string` reads the first `max_bytes` of a file (`File::take`), but every caller in `conversation.rs` uses it on `active.jsonl` — an append-only, still-growing log where the newest turns are at the *end*. Once a transcript exceeded the cap, `load_conversation_by_id` would silently show only the *oldest* turns and hide everything recent from the UI; `append_terminal_if_orphan` (whose own doc comment says "only the tail matters") would read a stale head-truncated window and could miss a genuine crash orphan at the real end of the file; and `session_id_for_conversation` (used by `promote_to_active` to resume a session) could resolve a stale mid-file session id instead of the real most-recent one. All three were previously an extreme, rarely-hit edge case; inline images make them realistic.
- **Consequences**: Added `limits::read_bounded_tail_to_string` — same lossy-decode contract as `read_bounded_to_string`, but seeks to `len - max_bytes` on an oversized file (logging a `warn!` with the path/len/cap, so the growth is now visible instead of silent) and drops the one partial leading line the seek may have landed inside, instead of the original's arbitrary trailing partial line. Switched the three tail-sensitive call sites in `conversation.rs` (`load_conversation_by_id`, `promote_to_active`, `append_terminal_if_orphan`) to the new reader. Left `list_conversations`'s per-file summary read on the original head-reader: `summarize` wants the *first* user turn for its excerpt, and a wrong `last_ts`/`turn_count` on an oversized file is a cosmetic history-list imprecision, not silent data loss or a broken resume — consistent with this module's documented "budgets are DoS guards, not correctness limits" stance for that one call site. `TRANSCRIPT_MAX_BYTES` itself is unchanged (16 MiB) — raising it doesn't fix the direction bug and a real image-heavy-conversation ceiling wasn't measured; the actionable fix was correctness (keep the relevant end), with the new `warn!` log giving real visibility into how often the cap is actually hit in practice, which is better evidence for a future resizing decision than a guess would be.
- **Detail**: 3 new tests in `limits.rs` (`read_bounded_tail_returns_full_small_file`, `read_bounded_tail_keeps_newest_lines`, `read_bounded_tail_missing_file_errors`). Gates green: `cargo fmt --check` / `cargo clippy --lib -- -D warnings` / `cargo test --lib` (524 passed, +3, 8 ignored). No frontend change, so `tsc`/`build` not run.

## 2026-08-03 — Route the secret scan through a real `loopdeck secret-scan` CLI instead of markdown-embedded `rg`

- **Status**: accepted
- **Context**: `prd-unattended-ship.md`'s two remaining gaps after PR #48 were both in the unattended draft-PR tail. The staged-diff secret scan (P1 goal) lived only as an inline `rg` pipeline inside the `loopdeck-open-pr` skill's old Phase 6a — run *after* Phase 5b's `git push`, so a hit was already on the remote by the time it fired. Worse, the scan itself ran `git diff --cached` at a point *after* Phase 5a's `git commit` had already cleared the staging area, so the check was silently scanning nothing. An "automated abort test" for this logic also had no home: this codebase has no shell-test harness (`grep`ped for one — only `scripts/smoke-test-release.sh` exists, unrelated), and CI runners aren't guaranteed to have `ripgrep` installed, so a bats-style test of the markdown's `rg` command would be flaky infrastructure this repo doesn't otherwise have.
- **Consequences**: Ported the same small v1 pattern set (AWS access key, PEM private-key header, GitHub/OpenAI-shaped tokens, generic `key|secret|token=` assignment — deliberately unchanged, per the PRD's own resolved Open Question) into a new `secret_scan.rs` module, using the `regex` crate (already an indirect dependency via `tracing-subscriber`'s `env-filter`, so promoting it to a direct one added no new crate to the dependency tree). A new `loopdeck secret-scan [--path <dir>]` CLI subcommand (wired in `main.rs`/`lib.rs`) mirrors the existing `loopdeck state` convention (Phase 3 of `prd-structured-execution-state`) of giving skill-driven checks one real, testable Rust definition instead of duplicating logic in markdown-embedded shell. Exit codes: `0` clean, `1` a pattern matched (abort), `2` the scan itself couldn't run (bad usage or a git/IO error) — distinct from `1` so the skill can tell "found a secret" from "couldn't check at all". The `loopdeck-open-pr` skill's Phase 5a now runs it immediately after `git add -A` and before the commit, for unattended pre-authorized runs only — the earliest point in the flow a hit can still be stopped before anything reaches the remote. 10 new Rust tests, including 3 CLI-level tests against real temp git repos (staged secret → exit 1, clean staged diff → exit 0, unknown flag → exit 2) that exercise the actual abort path end-to-end.
- **Detail**: Synced this repo's own tracked `.agents/skills/loopdeck-open-pr/SKILL.md` copy to the updated template by direct file copy (confirmed via diff it carried no local customization beyond being a stale mirror) — `.claude/skills/` (Claude-native) is gitignored and wasn't present in this worktree to sync. Did not bump `.agents/skills/.loopdeck-manifest.json`'s version field; that's tied to the app's own `refresh_skills` version-gated overwrite mechanism (`skills.rs`), a packaging-cadence concern out of scope here.

## 2026-08-03 — `prd-unattended-ship` PR-body metadata and budget-kill/worktree-lifecycle tests: extract the mechanism, don't mock the session

- **Status**: accepted
- **Context**: The PRD's remaining checklist items needed the unattended draft PR body to include a verify-verdict table and run metadata (phase id, budgets), plus dedicated test coverage for the budget-kill and worktree-lifecycle behavior described in `commands::run_queue::execute_run`. That function drives real `claude_session` turns with no mockable seam (a limitation already documented by every prior test-coverage decision touching this executor, e.g. the 2026-07-28 Phase 2 decision) and does real `git worktree` I/O — so full end-to-end coverage of `execute_run` itself was never on the table.
- **Consequences**: **PR body**: `run_executor::build_phase_prompt` gained a `ResolvedBudgets { phase_token_cap, phase_wall_clock_secs, run_wall_clock_secs }` parameter, resolved once in `execute_run` from `RunBudgets` defaults (no duplicate default-resolution logic). The unattended-authorized prompt branch now explicitly states the phase id and resolved budgets and instructs the agent to render them into a `## Run metadata` PR-body section verbatim (never recomputed or invented), plus a `## Verify Verdict` section reproducing the `loopdeck-prd-verifier` report the same turn already produced earlier in its own scrollback — no new plumbing needed since the agent already has that report in context. **Budget-kill test**: rather than attempt (and fail) to mock a live session, extracted `execute_run`'s inline `tokio::time::timeout(watchdog_timeout, turn)` race into a standalone `race_with_watchdog`/`WatchdogOutcome<T>` — the same extraction pattern this file already used for the worktree-bootstrap watchdog (`wait_for_bootstrap_child`/`BootstrapStop`, tested with a real stuck `sleep 30` child process). Unit-tested with a deliberately stuck fixture *future* (a 30s sleep raced against a 20ms budget) standing in for a wedged session turn — this proves the exact timeout-vs-real-work decision the executor's kill path depends on, which is the mechanism actually at risk, not a claim that a live process gets SIGKILLed (that reap path is `claude_session.rs`'s pre-existing `Drop` impl, out of this PRD's scope per its own Design section: "Kill path reuses the graceful EOF-then-SIGKILL reap that `claude_session`'s Drop already implements"). **Worktree lifecycle**: extracted the end-of-run cleanup block (prune on full success / keep+flag otherwise / keep+flag if the prune itself fails) into `finalize_worktree`, tested against real temp git repos alongside 3 new `ensure_worktree` tests (create, idempotent resume, missing-worktree error) — these needed no session at all, just real `git worktree` commands, so they get genuine integration coverage rather than a mechanism-only proxy.
- **Detail**: A same-day gotcha worth recording: the worktree lifecycle tests initially failed under parallel `cargo test` execution because `run_worktree_path` derives a run's worktree destination from `root.parent()/.loopdeck-runs/<plan.id>` — every test's temp repo shares the OS temp dir as `root.parent()`, so reusing the existing `plan()` test fixture's fixed `id: "run-budget-test"` made concurrent tests race to create a linked worktree at the identical path. Fixed by giving each worktree-lifecycle test plan a unique `uuid::Uuid::new_v4()`-derived id. 21 new Rust tests total across this decision and the one above. Gates green: `cargo fmt --check` / `cargo clippy --lib -- -D warnings` / `cargo test --lib` (545 passed, +21, 8 ignored). No frontend change, so `tsc`/`build` not run.

## 2026-08-03 — Multi-model runs use a global UUID roster and isolated durable sub-runs

- **Status**: accepted
- **Context**: The multi-model-agents epic needed reusable provider/model credentials and concurrent mixed Claude/Codex execution without sharing a checkout or letting restart/control races corrupt run state.
- **Consequences**: Named profiles live in the global registry with UUID-scoped owner-only secrets and legacy migration; one durable run manifest owns N agent-tagged sub-runs, provider turns execute concurrently in separate linked worktrees, and project-scoped admission/manifest locks serialize lifecycle transitions. Only pristine successful worktrees are removed; modified, failed, or cancelled worktrees remain inspectable. Claude and Codex share the crate-private `HarnessAdapter` contract while `HarnessSession` remains the stored enum.

## 2026-08-03 — Unattended runs own autonomous policy and root-scoped observability
- **Status**: accepted
- **Context**: Queue execution previously discarded its live stream, persisted transcripts under an isolated worktree, and inherited project manual-approval mode, making safe unattended work invisible or silently parked.
- **Consequences**: Run phases now force autonomous policy within the existing destructive safety floor, broadcast live events app-wide, persist project-visible transcripts, expose parked reasons and approval cards, and support dependency-aware unattended retry.
